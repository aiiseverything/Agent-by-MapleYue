# 第 1 章 · 零基础理解 LLM Agent

> **本章目标**：读完之后你能用自己的话回答下面三个问题——
> ① 大模型已经能对话了，为什么还需要 Agent？
> ② 一个 Agent 最小由哪几部分组成？
> ③ Agent 内部那个"循环"到底在循环什么？
>
> 本章**不出现任何代码**，先把心智模型建立起来。代码从第 2 章开始。

---

## 1.1 先搞清大模型到底是个什么东西

### 1.1.1 一句话定义

**大语言模型（LLM）本质上是一个函数：输入一段文本，输出下一段文本。**

就这么多。它做的事情是"预测下一个词"——给它 `今天天气真`，它会输出 `好` 的概率最高。
把这件事做到极致，就涌现出了对话、翻译、写代码、推理这些能力。

请记住这个定义，因为它直接推出了后面所有限制。**它是个纯函数：给同样的输入，得到同样的输出；
它不能"顺便"做任何别的事。**

### 1.1.2 三个致命限制

初学者最容易犯的错，是把大模型当成一个"懂很多、什么都能干"的智能体。
实际上它有硬性边界：

| 限制 | 具体表现 | 举例 |
| --- | --- | --- |
| **① 知识是冻结的** | 它只知道训练数据截止之前的事，也不知道任何实时信息 | 问它"我们公司昨天服务器的错误率是多少"，它只能编一个 |
| **② 不能执行动作** | 它只能输出文本。不能读文件、不能发 HTTP 请求、不能运行代码、不能写数据库 | 让它"帮我把 user.py 里的 bug 修掉"，它会输出一段"修改后的代码文本"，但**文件根本没变** |
| **③ 没有记忆** | 每次调用都是独立的。上次对话的内容它完全不记得 | 你先说"我叫小明"，下一轮问"我叫什么"，它不知道（除非你把前面的话**再发一遍**） |

第 ③ 条还有个更隐蔽的变体：即使你在一次请求里把历史都带上，**上下文窗口也是有长度上限的**。
超出上限的内容会被截断或报错。这就是"记忆管理"要解决的问题。

### 1.1.3 那"AI Agent"是什么？

一句话：

> **Agent = 让大模型能够"感知 → 思考 → 行动 → 再感知"的一整套工程结构。**

拆开说，就是我们用工程手段去补上大模型的那三个限制：

```
限制①「知识冻结、不知实时」  →  给它一个「搜索工具」，让它能主动查
限制②「不能执行动作」        →  给它一批「工具」，让它能读写文件、跑代码、调 API
限制③「没有记忆」            →  给它「记忆系统」，短期存对话、长期存事实
```

而这三种能力，**都不是模型自己长出来的，是外面这套框架喂给它的**。
这套框架，业界就叫 **Agent Harness**（"挽具"——套在马身上、把马力变成拉车动力的那套东西）。

> 本项目 `liteagent` 就是一个 **Agent Harness**。
> 它本身没有任何"智能"，它的全部工作是把大模型输出的**文本**，
> 可靠地翻译成现实世界的**动作**，再把动作的**结果**翻译回文本喂给模型。
>
> 这句话是理解整个项目的钥匙。项目里 41 个模块、2.4 万行代码，
> 本质上都在解决"翻译得准不准、稳不稳、出错怎么办"。

## 1.2 核心循环：Agent 的心跳

### 1.2.1 一个生活化的类比

想象你雇了一个**只会写字、但非常聪明**的顾问。他坐在一间没有窗户的办公室里，
唯一能和外界交互的方式是**递纸条**：

- 他递出来一张纸条：「请帮我查一下今天北京的天气」
- 你（作为跑腿的）去查了，把结果写在纸条上递回去：「晴，25 度」
- 他看了之后说：「那我建议穿短袖」，然后停下笔——**任务结束**

这个顾问就是**大模型**，你就是 **Agent 框架**，"递纸条"就是**工具调用**。

关键洞察：**顾问从始至终没有离开过办公室，所有真实世界的动作都是你替他做的。**

### 1.2.2 循环的四拍

把上面这个过程形式化，就是 Agent 的核心循环。注意每一步**谁在做事**：

```
       ┌─────────────────────────────────────────────────┐
       │                                                 │
       ▼                                                 │
 ┌───────────┐      ┌───────────┐      ┌───────────┐     │
 │  ① 思考   │─────▶│  ② 行动   │─────▶│  ③ 观察   │─────┘
 │  THINK    │      │   ACT     │      │  OBSERVE  │
 │           │      │           │      │           │
 │ 【模型】  │      │ 【框架】  │      │ 【框架】  │
 │ 输出一段  │      │ 解析模型  │      │ 执行工具  │
 │ 文本      │      │ 想调什么  │      │ 把结果变  │
 │           │      │ 工具      │      │ 成文本    │
 └───────────┘      └───────────┘      └───────────┘
       ▲
       │
   ┌─────────┐
   │ ④ 判断  │  【框架】任务完成了吗？超步数了吗？
   │  循环   │  没完成 → 回到 ①（把观察结果一起发给模型）
   └─────────┘  完成   → 返回最终答案
```

这里有个**极重要的分工**：

| 谁 | 负责什么 | 为什么这样分 |
| --- | --- | --- |
| **大模型** | 决策：下一步该干什么 | 只有它有"理解"和"推理"能力 |
| **框架** | 执行：真的去干，并把结果转成文本 | 模型碰不到真实世界，只能靠框架 |

**框架永远不替模型做决策，模型永远不亲自执行动作。** 这条边界一旦模糊，Agent 就会变得不可控。

### 1.2.3 为什么必须"循环"

因为一个真实任务往往要好几步。看这个例子——用户说：

> "帮我看看 `calculator.py` 里第 20 行是不是有 bug"

模型第一轮只能决定"我得先读到这个文件"：

```
第 1 轮：模型输出 → 我要调用 read_file(path="calculator.py")
        框架执行 → 读到文件内容："def safe_divide(a, b): return a / b"
        框架把内容作为"观察结果"喂回去
第 2 轮：模型看到内容 → 「啊，b 没做除零检查」→ 给出最终答案
```

**每一轮里，模型都能看到"之前所有轮次 + 刚才那次工具的结果"**，
所以它能一步步逼近答案。这就是 ReAct（**Rea**son + **Act**）循环。

> 单轮问答叫 Chatbot，多轮"思考-行动"才叫 Agent。
> 循环的次数上限、什么时候该停、停不下来怎么办——这是工程上最容易出问题的部分，
> 第 5 章会专门讲（本项目有五层防护）。

## 1.3 两种"让模型表达要调工具"的方式

模型只会输出文本。那"我要调用 `read_file`，参数是 `calculator.py`"这件事，
怎么用文本表达？业界有两套做法，**本项目两种都支持**：

### 方式 A：Function Calling（原生工具调用）

这是模型厂商提供的**官方能力**。你调用 API 时，除了发消息，还额外告诉它：

```jsonc
// 你告诉模型："你有这些工具可用"
"tools": [
  {
    "type": "function",
    "function": {
      "name": "read_file",
      "description": "读取一个文本文件",
      "parameters": { "type": "object", "properties": { "path": {"type": "string"} } }
    }
  }
]
```

模型如果决定用它，就会返回一个**结构化的字段**（而不是自然语言）：

```jsonc
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    { "id": "call_0", "function": { "name": "read_file", "arguments": "{\"path\": \"calculator.py\"}" } }
  ]
}
```

**优点**：格式由模型保证，解析几乎不会出错。
**缺点**：不是所有模型都支持；支持的模型之间格式也有差异；你要为每个厂商写适配。

### 方式 B：文本 ReAct（让模型"按格式写作文"）

在没有原生工具调用能力时（或者你想更强地控制推理过程时），可以约定一种文本格式，
让模型"照着写"，然后**框架用正则/解析器把文本解析成结构化的工具调用**：

```
Thought: 我需要先看看这个文件的内容
Action: read_file
Action Input: {"path": "calculator.py"}
```

框架解析出 `Action: read_file`，执行，然后把结果拼成：

```
Observation: def safe_divide(a, b): return a / b
```

再发回给模型，模型继续：

```
Thought: 找到了，b 没有做除零检查
Final Answer: 第 20 行的 safe_divide 缺少除零保护，建议加 if b == 0 的判断
```

**优点**：任何模型都能用；推理过程（Thought）是显式可见的，便于调试。
**缺点**：模型可能不按格式输出——这是**工程上最大的坑**，需要一套容错解析器（第 5 章讲）。

### 本项目的关键设计

`liteagent` 把这两种方式**归约到同一个数据结构** `list[ToolCall]`：

```
原生 function calling ──┐
                        ├──▶ list[ToolCall] ──▶ 同一个 ReAct 状态机
文本 ReAct 解析 ────────┘
```

所以**控制流只有一份**，两种模式只是它的两个入口。
这个设计的好处：新增一种"模型表达工具调用的方式"时，只要写一个解析器，不用改状态机。
（详见第 5 章和本项目 `docs/DESIGN_DECISIONS.md` 的 D-02。）

## 1.4 一个 Agent 的最小组成

抛开所有工程细节，一个能跑的 Agent 只需要四样东西：

| 组成 | 作用 | 本项目对应模块 |
| --- | --- | --- |
| **① 一个模型客户端** | 能发消息、收回复 | `liteagent/llm/` |
| **② 一组工具** | 模型能调用的外部能力 | `liteagent/tools/` |
| **③ 一个循环** | 把上面两者串起来反复跑 | `liteagent/agent/agent.py` |
| **④ 一段记忆** | 记住之前发生了什么 | `liteagent/memory/` |

这就是本项目"三层架构 + 一个循环"的由来：

```
┌──────────────────────────────────────────────────────┐
│                    Agent（循环 / 大脑皮层）           │
│         决定"什么时候调模型、什么时候调工具"          │
└───────┬──────────────┬───────────────┬───────────────┘
        │              │               │
   ┌────▼────┐   ┌─────▼─────┐   ┌─────▼──────┐
   │ LLM 层  │   │  工具系统  │   │  记忆管理   │
   │ 统一各家 │   │ 注册/校验/ │   │ 短期窗口    │
   │ 模型 API │   │ 并发/重试  │   │ 摘要压缩    │
   │         │   │           │   │ 长期向量    │
   └─────────┘   └───────────┘   └────────────┘
```

> **为什么值得分成三层？**
> 因为这三层的**变化频率完全不同**：
> 模型厂商 API 每几个月就变一次，工具是业务方天天在加，记忆策略是产品需求在调。
> 分层的意义是：换模型不该动工具代码，加工具不该动记忆代码。

## 1.5 多 Agent：当一个人干不完时

单个 Agent 能力有限，尤其是面对复杂任务时。一个自然的想法是：

> 让一个"主管 Agent"把任务拆成子任务，再派给几个"专员 Agent"分别去做。

这就是**多 Agent 协作**。本项目实现了两种最常用的模式：

| 模式 | 结构 | 适合什么任务 | 类比 |
| --- | --- | --- | --- |
| **Sequential（顺序）** | A → B → C 一条流水线 | 步骤固定的流程，如"调研 → 写作 → 校对" | 工厂流水线 |
| **Hierarchical（层级）** | 主管拆任务 → 派给多个专员 → 汇总 | 任务边界需要动态判断的 | 公司里的经理+员工 |

第 7 章会详细讲。这里你只需要先建立一个判断：

> **多 Agent 不是银弹。** 它带来的是"上下文隔离"和"职责分离"两个好处，
> 代价是通信开销、错误传播、以及**调试难度指数上升**。
> 能用单 Agent + 几个好工具解决的事，不要上多 Agent。

## 1.6 常见误解澄清

初学者最容易有的几个错误直觉，先在这里纠正：

**❌ 误解 1：Agent 是模型自己"进化"出来的**
✅ 实际上：Agent 的能力**几乎全部来自框架设计**。同一个模型，配上好的工具和好的循环控制，
表现天差地别。这也是为什么这个项目值得写——**框架才是工程量所在**。

**❌ 误解 2：模型会"记住"上一次对话**
✅ 实际上：不会。你看到的"记忆"都是框架每一轮**把历史重新发过去**实现的。
所以上下文窗口管理和记忆压缩是硬需求，不是优化项。

**❌ 误解 3：工具调用是模型在"执行"**
✅ 实际上：模型只是**输出了一段文本**说"我想调用某某工具"。
真正执行的是框架。这意味着**安全责任在框架**——模型可能要求执行 `rm -rf /`，
框架必须有能力拒绝。（第 4 章讲本项目的沙箱与审批机制。）

**❌ 误解 4：模型说"我修好了文件"，文件就真的改了**
✅ 实际上：如果框架没有真的去执行写文件操作，模型只是在"写作文"。
这是最危险的幻觉——**模型会自信地宣称它做了它根本没能力做的事**。
（本项目用工具返回值作为唯一的"事实来源"，模型的自述不算数。）

**❌ 误解 5：ReAct 里的 "Thought" 是模型的真实思考过程**
✅ 实际上：它是模型生成的文本，**有解释性但不是因果性的**。
模型可能先"决定"调工具，再补一段听起来合理的 Thought。
所以**不要用 Thought 做安全判断**，要用实际的工具调用和参数。

## 1.7 本章小结

把这一章压缩成五句话：

1. **LLM 是个纯函数**：输入文本 → 输出文本，它碰不到真实世界。
2. **Agent = 用工程手段给 LLM 补上"感知/行动/记忆"三种能力**的外壳（Harness）。
3. **核心是一个循环**：模型决策 → 框架执行 → 结果回灌 → 再决策，直到完成或触发停止条件。
4. **模型只决策，框架才执行**——这条边界是安全性的根基。
5. **框架的价值在于"翻译得准、稳、出错能兜住"**，而不是聪明。

2. Agent 循环里的四个阶段分别由谁负责（模型 or 框架）？
3. Function Calling 和文本 ReAct 的根本区别是什么？本项目为什么两者都支持？
4. "Harness（挽具）"这个比喻里，马和挽具分别指什么？
5. 为什么说"模型说它修好了"不能作为事实依据？

<details>
<summary>参考答案（点开）</summary>

1. 因为它只输出文本，没有执行能力；文件被改动必须由外部框架真的去调用文件写入。
2. 思考（模型）、行动（框架解析+执行）、观察（框架执行并转文本）、判断循环（框架）。
3. 前者由模型厂商保证输出结构化字段，后者靠约定文本格式 + 框架解析；本项目把两者归约到同一个
   `list[ToolCall]`，因此控制流唯一，只是入口不同。
4. 马 = 大模型（提供智能/推理能力），挽具 = Agent 框架（把智能转换成可用的动力输出）。
5. 因为模型只能输出文本，它没有能力知道文件是否真的被改了；唯一可信的事实来源是工具的实际返回值。
